## 1. 전체 프로젝트 구조 점검

### 1.1 구성 요소와 데이터 흐름

```text
[브라우저 Vue 대시보드]  app/web/static/*
        │ fetch /api/*, WS /ws  (X-Auth-Token 헤더 또는 ?token=)
        ▼
[FastAPI 대시보드 프로세스]  app/api/server.py, services.py, backtests.py, process.py
        │ SQLite 읽기·쓰기 (engine_status 읽기, bot_commands·bot_settings 쓰기)
        │ 공개 시세 REST (현재가·마켓 목록), 포켓 API (키가 있을 때)
        │ Start 만 예외: subprocess 로 `python -m app.main run` 실행
        ▼
[TradingEngine 프로세스]  app/trading/engine.py
        ├─ REST 캔들(닫힌 것만) → MarketState → Strategy.generate_signal
        ├─ WebSocket ticker/orderbook → MarketState.prices → check_exits (손절·익절·추적)
        ├─ RiskManager.evaluate / check_exits / record_trade / update_equity
        ├─ Broker: PaperBroker(가상) | LiveBroker(실제 시장가 주문)
        │       └─ UpbitClient.create_order / get_order / cancel_order / get_order_chance / get_accounts
        └─ Repository → SQLite (signals, orders, trades, round_trips, positions, accounts, balances, bot_logs,
                                  market_data, engine_status, bot_commands, bot_settings)
```

- **Dashboard → FastAPI → Trading Engine → Risk Manager → Order Manager → Upbit API** 구조는 유지되고 있다.
  - 프론트엔드(`app.js`)는 자체 API 만 호출하며 거래소 URL 을 직접 호출하는 코드가 없다. 매매 판단 로직도 없다.
  - 주문 생성 코드는 `LiveBroker.execute` 한 곳(`app/trading/live_broker.py:107-156`)뿐이고, 여기서만 `UpbitClient.create_order` 를 부른다. `create_order`/`cancel_order` 는 `allow_orders` 플래그(`upbit_client.py:145-150`)와 `assert_live_order_allowed`(`live_guard.py:30-39`) 두 잠금을 거친다.
  - 웹 서버는 주문 API 를 호출하지 않는다. 다만 `DashboardService.bot_client()`(`services.py:254-255`)가 `UpbitClient.from_settings` 로 만들기 때문에 `.env` 가 LIVE 이중 플래그면 **주문 가능한 클라이언트 객체가 대시보드 프로세스에도 존재**한다 (호출 코드는 없음 — LOW-13 참고).
- 엔진과 대시보드는 **같은 SQLite 파일**을 공유한다 (WAL). 두 프로세스의 조율 수단은 `engine_status` 하트비트(10초 주기, 45초 지나면 죽은 것으로 판정)와 `bot_commands` 큐(2초 폴링)뿐이다.
- 리스크 규칙은 `RuntimeSettings`(DB `bot_settings`)에서 읽어 `RiskManager` 에 주입되고, 주문 직전 `RiskManager.evaluate`(`risk/manager.py:159-214`) 가 예산을 정한다. LiveBroker 는 그 예산을 거래소 잔고와 `min` 해서 낸다 (`live_broker.py:169-170`).
- Docker / 배포 설정은 아직 없다 (Phase 10 예정). 프로세스 감시자(supervisor)·자동 재시작도 없다.

### 2.2 인증 / 권한 (대시보드)

`app/api/server.py:62-75`

```python
def require_auth(request):
```

- JWT/세션은 쓰지 않는다(고정 토큰). 토큰 비교는 `==` (비상수 시간), 쿼리스트링 `?token=` 도 허용(프록시 접근 로그·브라우저 히스토리에 남음), 실패 횟수 제한·지연 없음 (MEDIUM-10).

## 3. 실제 돈이 거래되는 부분 집중 감사

### 3.1 중복 주문 — **[재현 확인] CRITICAL-1**

`app/trading/live_broker.py:126-146`

```python
for attempt in range(1, self.max_attempts + 1):        # max_attempts 기본 2
    identifier = make_identifier(client_id, attempt)   # 2회째부터 "-r2" 접미사
    params["identifier"] = identifier
    try:
        info = await self.client.create_order(params); break
    except UpbitNetworkError as exc:                     # 응답을 못 받음 (타임아웃 등)
        info = await self._find_by_identifier(identifier)
        if info is not None: break                       # 찾으면 OK
        # 못 찾으면(404 또는 조회도 타임아웃) → 다음 attempt 에서 새 identifier 로 재주문
```

`_find_by_identifier`(`live_broker.py:191-199`)는 404 와 네트워크 오류 모두 `None` 을 돌려준다. 즉 아래 두 상황에서 **같은 신호로 주문이 두 번 나간다**:

1. `POST /v1/orders` 가 서버에는 도달했으나 응답이 타임아웃(`HTTP_TIMEOUT_SECONDS=10`) → 곧바로 한 `GET /v1/order?identifier=` 도 네트워크 불안정으로 실패 → `-r2` 로 재주문.
2. 응답 타임아웃 직후 조회했을 때 서버가 아직 주문을 반영하지 않아 404 → `-r2` 로 재주문.

재현 결과 (`FlakyClient` 로 1차 생성 타임아웃 + 조회 실패):

```text
[1] 거래소에 생성된 주문 수 = 2 | identifiers = ['c1', 'c1-r2'] | 내부 상태 = FILLED
[2] 404 후 재주문 재현:   거래소 주문 수 = 2 | identifiers = ['c1', 'c1-r2']
```

- 시장가 **매수**는 `amount = min(요청 예산, 거래소 KRW 잔고)`(`live_broker.py:169-170`) 이므로 `RISK_MAX_ORDER_AMOUNT` 나 `POSITION_FRACTION<1` 처럼 잔고보다 작은 예산을 쓰는 **안전한 설정일수록** 두 번째 주문도 체결된다 (잔고 전액 매수 설정에서는 두 번째가 `insufficient_funds_bid` 로 거부된다).
- 매도는 두 번째가 잔고 부족으로 거부되므로 피해가 제한적이다.
- 내부 상태는 두 번째 주문만 반영하고 첫 주문은 다음 `reconcile`(최대 300초 뒤)에서야 포지션에 합쳐진다. 그 사이 손절 감시는 절반 수량만 본다.
- 기존 테스트 `test_network_error_without_order_is_rejected` 는 "1차·2차 모두 생성 실패" 만 검증해 이 경로를 놓친다.

### 3.2 Race Condition

- **같은 코인 동시 매수**: 전략 신호는 `strategy_signals` 유니크 제약(`models.py:59`)과 `client_id`(신호 시각 기반)로 막힌다. 엔진 두 개가 떠도 신호 하나는 한 번만 처리된다 (양호). 그러나 청산 주문의 `client_id` 는 `now.isoformat()` 을 포함해(`engine.py:410`) 항상 새 값이므로 중복 방지 대상이 아니다.
- **같은 포지션 중복 처리**: 메인 루프의 `check_exits(force=True)`(`engine.py:656`) 와 시세 루프의 `check_exits`(`engine.py:580`) 가 동시에 돌 수 있다. LiveBroker 는 `GET /v1/orders/chance` 로 가용 잔고를 다시 읽으므로 두 번째 매도는 대개 "매도할 수량이 없습니다" 로 거부된다. 둘 다 `chance` 를 먼저 읽고 나서 주문하면 두 번째는 업비트가 잔고 부족으로 거부한다 — 자체 방어가 아니라 거래소에 기대는 구조다.
- **잔고 갱신 전 추가 주문**: LIVE 는 주문마다 거래소 잔고를 읽으므로 없음. PAPER 는 동기 코드라 없음.
- **reconcile 와 진행 중 주문의 경합** (MEDIUM-3): `reconcile` 은 `Account.balance` (주문에 묶인 `locked` 제외)만 본다(`live_broker.py:62, 69`). 시세 루프에서 낸 시장가 매도가 체결 대기 중일 때 메인 루프의 스냅샷 `reconcile`(`engine.py:664-667`) 이 돌면 코인 `balance` 가 0 이라 **내부 포지션을 삭제**한다(`live_broker.py:274-276`). 이후 `_apply_fill` 의 `portfolio.sell` 이 `PortfolioError("포지션이 없습니다")` 를 내고 주문은 "체결됐지만 내부 계좌 반영 실패" 로 REJECTED 처리된다(`live_broker.py:239-242`). 왕복 거래(`round_trips`)가 저장되지 않아 연속 손실·당일 손익이 반영되지 않는다.
- **WebSocket 과 REST 데이터 불일치**: `mark_price` 가 호가(WS)를 체결가(REST 보정)보다 무조건 우선한다 — CRITICAL-2.

### 3.3 주문 상태 관리 — **[재현 확인] HIGH-1**

내부 `OrderStatus` 는 `NEW / FILLED / REJECTED` 세 가지뿐이다(`orders.py:23-26`). 요구 상태 중 `SUBMITTED / OPEN / PARTIALLY_FILLED / CANCELLED / UNKNOWN` 이 없다.

| 실제 상황 | 내부 기록 | 결과 |
| --- | --- | --- |
| 주문 생성 후 체결 조회(`_wait_for_fill`)가 네트워크 오류 | `REJECTED` + "체결 확인 실패 (…남아 있을 수 있음)" (`live_broker.py:150-155`) | 계좌 미반영. **[재현 확인]** 거래소 주문 1건 존재, 내부 현금 차감 0, 포지션 없음 |
| 부분 체결 후 취소 | `FILLED` + reason 에 "(부분 체결 후 취소)" | 수량은 맞지만 상태값이 부분체결을 표현하지 못함 |
| 30초 내 미체결 → 취소 접수 → 그 사이 체결 | 취소 후 한 번만 재조회(`live_broker.py:214-215`) | 취소 반영 전 체결분이 누락될 수 있음 (다음 reconcile 로 복구) |

UNKNOWN 이 REJECTED 로 축약되면 엔진은 "아무 일도 없었다" 고 판단한다:

- **매수가 실제로 체결된 경우**: 포지션이 내부에 없으므로 손절·익절 감시가 없다. 다음 `reconcile`(≤300초) 뒤에야 `opened_at=지금, entry_fee=0` 으로 편입된다.
- **매도(손절)가 실제로 체결된 경우**: 내부 포지션이 남아 있어 `check_exits` 가 **1초마다** 다시 매도를 시도한다(`engine.py:379-381` 의 1초 스로틀). 매번 `GET /v1/orders/chance` → "매도할 수량이 없습니다" → `orders` 테이블·`bot_logs`·`ORDER_REJECTED` 알림이 1초에 하나씩 쌓인다 (알림은 key 가 없어 쿨다운 없음, `engine.py:362-363`). reconcile 까지 최대 300건.

### 3.4 그 밖의 주문 경로 문제

- **[재현 확인] MEDIUM-1** `_apply_fill` 의 평균가 폴백: `trades` 가 비어 있으면 `avg_price = float(info.price)` 를 쓴다(`live_broker.py:226-227`). 시장가 매수(`ord_type=price`)의 `price` 는 **단가가 아니라 주문 총액(KRW)** 이다. 재현: 총액 100,000원·체결 0.001 BTC 응답에서 포지션 평균가 100,000원, 현금 차감 150원으로 기록됐다 (실제 단가 1억, 차감 10만원). 이 상태에서 손절가는 95,000원이 되어 사실상 손절이 꺼진다. `_wait_for_fill` 이 `trades` 없으면 한 번 재조회하지만(`live_broker.py:216-217`) 두 번째도 비어 있으면 그대로 진행한다.
- **LiveBroker 는 시세 신선도·괴리를 전혀 보지 않는다** (MEDIUM-6): `execute(request, price, now)` 의 `price` 인자를 쓰지 않는다. PaperBroker 는 30초 이상 오래된 시세를 거부하지만 LiveBroker 는 시세가 없어도 시장가로 낸다. 매수 괴리 검사(`manager.py:188-196`)는 `mark_price` 가 없으면 건너뛴다(`has_mark` False).
- `market_sell_params` 는 `f"{volume:.8f}"` 로 **반올림**한다(`upbit_client.py:305`). 잔고를 `float` 로 바꾼 뒤 포맷하므로 이론상 1e-8 만큼 잔고를 초과해 `insufficient_funds_ask` 가 날 수 있다 (LOW-7).
- `chance.max_total`(거래소 최대 주문 금액)을 파싱만 하고 강제하지 않는다 (LOW-12). 업비트가 거부하므로 손실은 없다.

## 4. 잔고 / 포지션 계산 검증

| 계산 | 구현 | 판정 |
| --- | --- | --- |
| 평균 매수가 | `Portfolio.buy` 가중평균(수수료 제외), `cost_basis` 에 수수료 포함 (`portfolio.py:191-197`) | 정확 |
| 보유 수량 | 8자리 내림 `floor_quantity` | 정확 |
| 평가 금액 | `quantity × mark_price` | 계산은 맞으나 `mark_price` 가 오래된 호가일 수 있음 (CRITICAL-2) |
| 실현 손익 | `proceeds − fee − entry_amount − entry_fee` (`portfolio.py:231`) | 정확. LIVE 는 재시작·reconcile 후 `entry_fee=0` 이라 매수 수수료(0.05%)만큼 과대 (LOW-8) |
| 미실현 손익 | `market_value − cost_basis` | 정확 |
| 수수료 | LIVE 는 `paid_fee` 그대로, PAPER 는 요율 | 정확 |
| 총 자산 | 현금 + 평가액. LIVE 현금 = KRW `balance`(`locked` 제외) | 주문 대기 중 일시 과소 (허용 범위) |
| 수익률 | `equity / initial_cash − 1` (`services.py:183`) | LIVE `initial_cash` 는 **첫 실행 시 KRW 잔고**로 고정. 포켓 이전으로 입출금하면 즉시 왜곡 (MEDIUM-4) |
| 포지션 비율 | `invested = equity − cash`, `room = ratio×equity − invested` (`manager.py:201-209`) | 정확 |
| MDD | `balances` 스냅샷(300초 + 체결 시) 기반 | 근사치 — 스냅샷 사이의 낙폭은 놓침 |

### 4.1 재시작 시 DB · 거래소 잔고 · 주문 상태 동기화

- **PAPER**: DB `accounts`/`positions` 에서 복구(`repository.py:175-192`), 처리한 `client_id` 5,000건 복구. 단, `_record_order` 가 `save_order → save_fill → save_round_trip → sync_portfolio → log → snapshot` 을 **각각 별도 트랜잭션**으로 실행한다(`engine.py:328-356`, `repository.py:60-130`). 중간에 죽으면 주문은 FILLED 인데 계좌·포지션은 이전 값인 상태로 복구된다 (MEDIUM-7).
- **LIVE**: 시작 시 `GET /v1/accounts` 로 계좌를 만들고(`main.py:306-311`), DB 의 포지션 기록은 쓰지 않는다. 이후 스냅샷 주기(300초)마다 `reconcile` 로 거래소 기준으로 덮어쓴다(`engine.py:664-667`). 따라서 **거래소와 DB 가 다르면 거래소가 이긴다** — 방향은 맞지만:
  - 복구된 포지션은 `opened_at=지금`, `entry_fee=0`, `avg_price=업비트 avg_buy_price` 다. `avg_buy_price` 가 0 인 자산(예: 포켓 이전으로 들어온 코인, `avg_buy_price_modified` 케이스)은 손절 기준가가 0 이 되어 **손절이 영구히 발동하지 않는다** — **[재현 확인]** 가격 1원까지 떨어져도 `check_exits` 가 `None` (MEDIUM-2).
  - 잔고가 0 보다 크기만 하면 포지션으로 편입하므로(`live_broker.py:69`) 최소 주문 금액 미만의 **먼지 잔고**도 포지션이 된다. 그러면 `has_position` 이 참이라 그 마켓은 다시 매수하지 못하고(`manager.py:179-180`), 손절 조건이 되면 매도 시도가 `under_min_total_ask` 로 거부되며 1초마다 반복된다 (MEDIUM-2).
- **재시작 중 주문 체결** (12절 시나리오 10): 신호는 주문 전에 저장되므로(`engine.py:248`) 같은 신호로 재주문하지는 않는다 (양호). 대신 그 주문은 어디에도 기록되지 않고 reconcile 로만 포지션에 나타난다.
- **리스크 상태**: `rebuild` 가 오늘 `round_trips` 로 연속 손실·당일 실현손익을 복구한다(`manager.py:130-139`). 그러나 `day_start_equity` 를 **재시작 시점의 자산**으로 놓기 때문에 일일 손실 한도의 기준선이 매 재시작마다 초기화된다 — HIGH-3. `halted`(긴급 정지)와 `lock_reason` 도 영속되지 않는다.

### 5.2 프론트엔드 조작 / API 직접 호출

- 리스크 값은 `PUT /api/settings` → `RuntimeSettings`(pydantic, `extra="forbid"`) → DB 버전 → 엔진이 캔들 경계에서 읽는다. 값 범위는 `RiskConfig`(`risk/config.py:25-45`) 가 검증한다. 잘못된 값은 엔진이 거부하고 로그를 남긴다(`engine.py:461-468`) (양호).
- 인증된 사용자는 손절·일일 한도·연속 손실 등 **모든 규칙을 None 으로 꺼서 저장**할 수 있다. 관리자 기능이므로 취약점은 아니지만, HIGH-5 의 인증 약점과 결합하면 위험이 커진다. "규칙을 끄는 저장" 에 대한 별도 확인·감사 로그(누가·언제)는 없다.
- 엔진 외부에서 주문을 낼 경로는 없다 (양호).

### CRITICAL-2 상세 — 오래된 호가를 평가·손절 판정에 사용 **[재현 확인]**

```python
# market_state.py:34-39
@property
def mark_price(self):
    if self.best_bid and self.best_ask:       # 호가가 있기만 하면 시각과 무관하게 우선
        return (self.best_bid + self.best_ask) / 2
    return self.last_price
# market_state.py:30-32  is_fresh 는 max(last_time, book_time) 기준
# engine.py:430-431      REST 보정은 set_last_price 만 호출 → best_bid/ask, book_time 은 그대로
# engine.py:393          check_exits: is_fresh 통과 → price.mark_price 로 손절 판정
```

WebSocket 이 끊긴 채 REST 보정이 돌면 `last_time` 은 방금, `book_time` 은 몇 시간 전이다. `is_fresh` 는 참, `mark_price` 는 **몇 시간 전 호가 중간값**이다. 재현: 3시간 전 호가 1억, 방금 REST 체결가 8천만 → `is_fresh=True`, `mark_price=1억`. 이 값이 손절(`check_exits`), 일일 손실(`current_equity → update_equity`), 매수 괴리 검사(`evaluate`), 자산 스냅샷에 모두 쓰인다. 즉 **WS 장애 중 가격이 20% 폭락해도 손절이 발동하지 않는다.** 반대로 상승장에선 익절이 발동하지 않는다.

Heartbeat / stale detection 판정: 연결 수준의 stale 감지(120초)는 있으나 **마켓별·데이터 종류별(호가 vs 체결) 신선도 검사가 없다**. 유동성이 낮은 코인은 호가 메시지 없이 수 분이 지날 수 있으므로 종류별 시각 검사가 필요하다.

### HIGH-2 상세 — 시세 루프 영구 종료 **[재현 확인]**

`engine.py:583-587` 은 `_price_loop` 의 모든 예외를 잡아 로그만 남기고 **루프를 끝낸다**. 루프 안에서 `check_exits → broker.execute → repo.save_order` 가 도는데, 여기서 `TraderError` 가 아닌 예외(SQLite `OperationalError: database is locked`, `UpbitResponseError` 아닌 파싱 예외, `KeyError` 등)가 나면 루프가 죽는다. 재현: 손절 조건 도달 → 매도 실행 → `repo.save_order` 가 `OperationalError("database is locked")` → `_price_loop` 가 정상 반환으로 끝남(태스크 종료, `stats.errors=1`, `price_stream_failed` 로그만 남고 재생성 없음, 엔진 status 는 그대로). LIVE 라면 이 시점에 주문은 이미 거래소에 나가 있고 DB 기록만 빠진 상태다. 이후 손절 감시는 **캔들 경계(예: 매시 정각)에서 한 번**뿐이다. WS 치명 오류(`UpbitWebSocketError`)도 같은 경로다. 하트비트 `ws_status` 는 마지막 상태를 보여줄 뿐 운영자에게 "감시 중단" 을 알리지 않는다.

**실시간과 백테스트가 달라질 수 있는 지점** (전략 자체보다 엔진 연결 부분):

1. **정체 후 신호 일괄 실행** — **[재현 확인] HIGH-4**. `process_closed_candles` 는 최근 `refresh_candles=5` 개를 받아 **새로 닫힌 캔들마다** 전략을 돌리고 즉시 주문한다(`engine.py:225-243`). 엔진이 몇 시간 멈췄다(네트워크 장애·PC 절전·DB 잠금) 깨어나면 지난 캔들의 BUY/SELL 이 **지금 가격**으로 연달아 실행된다. 재현: 3시간 정체 후 10:00 BUY, 11:00 SELL 이 현재가 150 에 연속 체결되어 즉시 손실(-4,821원) — 백테스트는 각 캔들 다음 시가에 체결한다고 가정하므로 실거래 결과가 달라진다. 괴리 검사(10%)가 유일한 방어이며 SELL 에는 적용되지 않는다.
2. **캔들 공백** — 5개 넘게 놓치면 그 사이 캔들이 롤링 프레임에 영구히 빠진다. `merge_candles` 에 연속성 검사가 없어 SMA/RSI 가 공백을 모른 채 계산된다. `validate_candles` 도 "간격이 너무 짧음" 만 검사하고 누락은 보지 않는다(`data.py:133-137`).
3. **신호 캔들 종가 vs 체결가** — 백테스트는 다음 캔들 시가, 실거래는 경계 + 3초의 호가. 정상 상황에선 근접하지만 급변 시 차이가 난다 (괴리 검사로 완화).
4. **엔진 경로에 OHLC 검증 없음** — 0 이하 가격·고저 모순 캔들이 와도 그대로 전략에 들어간다 (MEDIUM-13).
5. **1w / 1M / 1y** 캔들 경계는 `epoch // interval_seconds` 로 계산해(`engine.py:65-69`) 업비트의 주 시작(월요일)·월 시작과 어긋난다 (LOW-5).
